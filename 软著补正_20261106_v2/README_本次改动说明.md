### 10.5 一处已知偏差（如实说明）

说明书**第 1–9 页**的页码右端为 539.8pt，比版心右边界短 **4.4pt（约 1.55mm）**；第 10–32 页精确落在 544.2pt。

- 原因：WPS 导出时对 `PAGE` 域按"两位数宽度"预留了整块宽度（块起点恒为 458.8pt），个位数页码在该块内左对齐，于是右端少一个数字的宽度（4.4pt）。属 WPS 的域宽度缓存行为，不是制表位设置错误——把 `Header` 样式的默认制表位清掉后，60 页源程序（页码为字面文字、逐节排版）已能做到 566.9pt 全一致。
- 已尝试无效：调整 `Repaginate()` / `Fields.Update()` 顺序（先 Repaginate 再 Update 再 Repaginate），偏差不变。
- 若要求严格像素级对齐，可改用 `PAGE \# "00"` 补零，使个位数页显示「第 01 页」，宽度恒定后右端会精确到 544.2pt；代价是页码写法变成两位数补零、且与源程序的「第 1 页」不一致。**本轮未采用**：1.55mm 在打印件上不可辨，而两份材料页码写法一致更重要。

### 12.2 emoji 修复的四个实测坑（WPS 文字 COM 导出）

1. **只指定字体不够，要四属性全设**：run 的 rFonts 需同时设 ascii/hAnsi/eastAsia/cs = Segoe UI Emoji；该字体为 Windows 7+ 自带，导出为单色轮廓字形（非彩色），与代码文档风格一致。
2. **中文夹挤 + VS16 才是真坑**：普通 emoji（🎤🔑👥）即使被中文前后夹挤也能正常回退；唯独带变体选择符 U+FE0F 的 🗑️ 在"表头🗑️清空"这种中文夹挤下仍回退成方框。解法：该 run 文本首尾各加一个零宽空格 U+200B（零宽不可见、不折版心、不影响语义；全文仅 2 个，在注释中）。结论经 POC2/POC3/POC4 四组对照实验得出。
3. **BMP 符号不要误伤**：★（U+2605）、⚠（U+26A0，含带 VS16 的 ⚠️）宋体本就有字形，旧版显示正常；emoji 判定收窄为仅非 BMP 码位（1F000–1FAFF），VS16/ZWJ/键帽符仅在已处于 emoji 段时跟随并入。
4. **Python 布尔陷阱曾导致一次空白 PDF**：状态机里 `em = f(ch) or (buf_is_emoji and ...)`，首字符时 `buf_is_emoji=None` 使 em 得 `None` 而非 `False`，每字符都被误判为段首→全部普通 run 丢失→docx 3266 段落全空→WPS 导出 60 页只有页眉的 204KB 空白 PDF。已用 `bool(...)` 包裹修复。**教训：改排版脚本后先查 docx 内 w:t 数量/关键字，再导 PDF。**

文本层说明：WPS 对 Segoe UI Emoji 导出的 ToUnicode 映射缺失，PDF 文本提取时 emoji 仍呈 U+FFFD（旧版同样如此），不影响视觉、打印与审查；逐行核对按"emoji/缺字同归一"口径，新 PDF 与 JSON、与旧 PDF 均为零差异。
