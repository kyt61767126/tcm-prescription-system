# 热更新一键回滚 SOP（操作手册）

> 工具：`tools/rollback-hotupdate.cjs` ｜ 一键入口：`一键回滚热包.bat`
> 适用人：管理员/开发 ｜ 版本：2026-09-16 ｜ 详细背景见 KNOWLEDGE.md「热更新一键回滚」条目

---

## 1. 这是什么、什么时候用

**一句话**：热更新（软更新）发出去的版本有问题时，把客户端整体恢复到之前的正常版本，**不用重装 APP、不用重发 exe**。

**什么时候用**：

| 现象 | 用本工具？ |
|---|---|
| 发了热包后用户反馈功能坏/页面异常（签名合法但内容有 bug） | ✅ 用 |
| 客户端验签/哈希失败自动回退了打包版（静默，用户无感） | ❌ 不用（三道门禁已自动兜底，修好源头重新发版即可） |
| APK / exe 整包出了问题 | ❌ 不适用（本工具只管热包内容层，整包走发布流程） |
| 云端网页（public/ 直接部署）出问题 | ❌ 不适用（直接 git revert 源码重新 push 即可） |

**原理**：热包是全量快照，客户端只认「更高的版本号」。把旧版本内容重新签名、发布为更高版本号，全体客户端视为"升级"→ 自动下载恢复。零客户端改动，覆盖全部在装设备。

**支持三个渠道**：

| 渠道 | 覆盖端 |
|---|---|
| app-local | 离线APP |
| local | 离线桌面 |
| cloud | 云桌面 |

## 2. 标准操作（推荐：双击 bat）

**前提**：在开发机上进行（需要 git 历史完整 + 私钥 `tools/secrets/LICENSE_SIGN_ED25519_PRIVATE_KEY.pem`）。

双击项目根目录 **`一键回滚热包.bat`**，按提示回答 5 个问题：

```
输入 1/2/3:                    ← 选渠道（1=离线APP 2=离线桌面 3=云桌面）
回滚到哪个版本:                 ← 直接回车 = 上一版（最常用）
回滚范围:                       ← 直接回车 = 整包回滚（最常用）
确认执行写盘？(y/n):            ← y（上面会先展示回滚计划，看清"实际变化"再确认）
立即提交并推送发布？(Y/n):       ← 直接回车 = 立即发布（触发 CF Pages 部署）
```

**发布后 2-3 分钟生效**。验证：浏览器打开（以离线APP为例）

```
https://tcm-prescription-system.pages.dev/hot-update/app-local/version.json
```

确认 `hotVersion` 已变成回滚后的新版本号即部署成功。桌面端把路径换成 `/hot-update/desktop/local/version.json` 或 `/hot-update/desktop/cloud/version.json`。

## 3. 决策树：怎么选

### 选版本：回到哪个？

- **默认回上一版**（回车即可）——90% 的场景：刚发的版本有问题，退回上一个正常版。
- **回更早版本**——输入版本号（如 `2026.09.14-6`）。适用于：上一版也有问题，或要退到某个已知稳定版。

### 选范围：整包还是单文件？

- **整包回滚（默认）**：新热包大面积翻车、不确定哪个文件坏了 → 整体退回，最稳。
- **单文件回滚（输入文件名，逗号分隔）**：明确只有某一个文件坏（如只有 `auth-core.js` 有 bug），其余新内容没问题想保住 → 只退这个文件，**其他文件客户端零重下，秒级完成**。

> 拿不准就整包回滚。单文件是精确手术，整包是保命大招。

### 回滚后修好了 bug 想再上新版？

正常走发版流程（generate-app-hotupdate / generate-desktop-hotupdate）即可。版本号继续向上，与回滚互不冲突。

## 4. CLI 模式（高级 / 脚本化）

```powershell
# 列出某渠道全部历史版本（看有哪些可回滚）
node tools/rollback-hotupdate.cjs -c app-local --list

# 整包回滚到上一版（--dry-run 只看计划不写盘）
node tools/rollback-hotupdate.cjs -c app-local --dry-run
node tools/rollback-hotupdate.cjs -c app-local --yes

# 回滚到指定版本
node tools/rollback-hotupdate.cjs -c local -v 2026.09.15-7 --yes

# 只回滚指定文件（其余保持线上现状）
node tools/rollback-hotupdate.cjs -c cloud -f auth-core.js --yes

# 写盘后手动发布（工具也会打印这三条命令）
git add public/hot-update/desktop/cloud
git commit -m "hotfix(热更回滚): cloud 回滚至 <版本>"
git push
```

| 参数 | 说明 |
|---|---|
| `-c` | 渠道：`app-local` / `local` / `cloud` |
| `--list` | 只列历史版本 |
| `-v` | 指定回滚目标版本号（默认上一版） |
| `-f` | 只回滚指定文件（逗号分隔） |
| `--dry-run` | 只打印回滚计划，不写盘 |
| `--yes` | 非交互模式必须显式传才写盘（防手滑） |
| `--interactive` | 交互菜单（bat 的入口就是这个） |

## 5. 恢复时效（用户什么时候恢复正常）

| 环节 | 时间 |
|---|---|
| 回滚工具执行 + git push | ~1 分钟 |
| CF Pages 自动部署 | 2-3 分钟 |
| 客户端拉取 | 下次启动自动生效 |
| 离线APP 292+（登录页空闲、未在输入时） | **当次打开即生效**（智能热重载） |

即：**营业时间发现问题，5 分钟内线上已切回旧版，用户下次打开软件/APP 即恢复**。

## 6. 回滚的回滚（后悔药）

想撤销本次回滚、回到回滚前的版本？**再跑一次工具，目标版本选回滚前的版本号**即可。操作完全对称，工具会如实提示。

---

## 7. 安全机制（为什么可以放心操作）

- **先看后做**：写盘前必展示回滚计划（当前版本 → 目标版本 → 实际变化文件清单）。
- **minAppCode 只降不升**：自动取当前与目标中较小值，回滚绝不会把老版本用户挡在门外。
- **哈希从 git 历史重算**：不沿用旧清单哈希，顺带自动修正历史遗留的 CRLF 清单病。
- **零变化硬中止**：目标内容与线上完全一致时直接拒绝（exit 1），防止发布无意义版本。
- **写盘后回读复验 + 签名自验**：任何一项失败自动 `git checkout` 还原渠道目录，工作区不留残局。
- **未推送前一切可逆**：写盘了但没推送？`git checkout -- public/hot-update/` 即可丢弃。

## 8. 常见问题

| 问题 | 处理 |
|---|---|
| `回滚目标内容与当前线上完全一致（0 个文件变化）` | 该版本与线上内容相同（如纯哈希修复版），无事可做，工具已自动中止 |
| `git 历史缺文件: xxx` | 该提交历史不完整（极少见）。换一个目标版本 |
| `签名自验失败（私钥与客户端公钥常量不匹配）` | 本机私钥不对/缺失。在正确的开发机上操作（`tools/secrets/` 下） |
| 列表里看不到刚发的版本 | 该渠道目录 version.json 的提交未入库或未推送。先 `git status` 确认 |
| 回滚推送了但用户还是坏的 | ① 等 2-3 分钟 CF Pages 部署完；② 用户需重启软件/APP；③ 浏览器打开 version.json 确认版本号已变 |

## 9. 边界与红线

- 只回滚**热包内容层**（HTML/JS 业务代码）。APK、exe 整包、云端网页不在此范围。
- license 链、config.json 本就不进热包，回滚永远碰不到授权数据，用户激活状态/处方数据零影响。
- **禁止 force-push 改写热包历史**——git 历史是回滚唯一素材源。
- 签名消息构造现有 4 份实现（Java 客户端 / 两个生成工具 / 本回滚工具）必须逐字符一致，改一处必改其余三处（开发侧红线，非操作项）。
