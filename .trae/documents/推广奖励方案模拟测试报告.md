## 一、测试目标与方法

### 1.1 业务规则（方案定版）

| 规则 | 内容 |
|---|---|
| 邀请人奖励 | 每成功邀请 1 名付费激活用户 **+90 天**，阶梯累计：1人/90天、2人/180天、3人/270天、**4人/360天（封顶）** |
| 被邀请人奖励 | 通过好友邀请码激活，本人立即 **+30 天** |
| 到期锚定 | 到期时间 = **首次激活时间 + 365天 + 累计奖励天数**，重装/换机重激活不改变锚点（防"重装续命"） |
| 邀请码 | 激活成功即自动生成 6 位专属邀请码（去易混淆字符 I/L/O/0/1），全局唯一 |
| 计奖条件 | 仅**新设备首次付费激活**计奖（试用不计、同设备重复激活不计） |

### 1.2 测试方法

- **真实代码路径**：不 mock 业务逻辑，直接 import 生产 API 入口（`validate.js` / `invite.js` / `verify.js` / `admin-usage.js`），仅用内存 Map 模拟 Cloudflare KV 绑定。
- **覆盖四个角色**：管理员（发码/监控）、邀请人 A、被邀请人 B~F、试用用户 T。
- **验证三层**：业务返回值（奖励天数/进度）→ KV 持久化记录 → 审计日志链。
- 测试脚本为一次性临时文件（已删除），未改动任何产品代码，**无需重新打包任何客户端**。

## 三、测试中的修正点（2 处，均为测试侧，非产品缺陷）

### 修正点 1：试用激活码测试数据使用了非法字符

- **现象**：阶段 7 首跑时试用码激活失败，返回"激活码格式错误"。
- **根因**：测试自造的试用码 `BNZC-TRI2-ALCD-EFGH-KLMN` 含字符 `L`（激活码字符集 `A-HJ-NP-Z2-9` 专门排除了易混淆的 I/L/O/0/1），被格式校验正确拒绝。
- **处置**：改为合法字符 `BNZC-T2R2-ABCD-EFGH-KMNP` 后通过。
- **结论**：**这是格式校验按设计工作的正面验证**，反而证明激活码生成/校验的字符集约束有效。

### 修正点 2：累计奖励天数的预期值算错（认知澄清）

- **现象**：阶段 11 首跑时 `rewardDaysTotal=480`，最初断言预期 390（A 的 360 + B 的 30），判定失败，疑似多发奖 bug。
- **核查过程**：逐条打印 KV 中全部激活码的邀请字段分布，发现 C/D/E 作为被邀人**各持 30 天奖励**——发放明细与规则完全一致。
- **结论**：**480 是正确值**：360（A 的邀请奖励 4×90）+ 4×30（B/C/D/E 被邀奖励）。最初遗漏了"C/D/E 也是被邀请人"这层。该行为与客户端界面提示"双方都得奖励（好友+90天，您+30天）"完全一致。
- **修正**：更新断言为 480，并补充 C/D/E 被邀人到期日（395 天）验证项，全部通过。

## 五、结论与建议

### 5.1 结论

1. **功能链路完整可用**：发码 → 激活 → 邀请 → 发奖 → 记账 → 到账生效（重激活领取）→ 审计 → 后台监控，端到端无阻断。
2. **奖励数值精确**：阶梯 90/180/270/360 封顶、被邀人 +30 立即生效、到期日锚定首次激活不受重装影响，全部与定版规则一致。
3. **风控稳健**："宁可漏发不可误伤"原则贯彻到位——所有异常邀请场景均不阻断正常激活，且留有完整审计痕迹。
4. **零产品缺陷**：测试期间未发现需要修改产品代码的问题；2 处修正均为测试侧数据/断言问题。

### 5.2 上线状态

### 5.3 后续建议（非阻塞）

1. **观察期**：上线后 2~4 周在管理后台「📊 用量监控」Tab 观察邀请增长与 KV 写入量（免费额度风险线约 33 家活跃诊所）。
2. **防环场景**：本次模拟未覆盖"A 邀 B 后 B 再邀 A"的互邀套利组合，代码已实现拦截，建议下轮补测。
3. **用户引导**：可在帮助文档中说明"奖励为记账制，邀请成功后重新激活一次即可领取延期"，降低用户咨询量。
