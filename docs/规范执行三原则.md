# 规范执行三原则

> 适用于本项目所有"规范"：界面结构保护、安全防护、打包分发、版本一致性、文件命名等。
> 目的：防止规范只写了"该做什么"，却在执行中静默失效（如双套脚本冲突、基线过期、报错不可行动）。
> 更新时间：2026-08-18 | 依据 commit 81343574

---

## 原则一：一个事实只有一个权威源

- 任何会被反复校验的东西，必须收敛到**唯一一份入库文件**。
- 出现同名/同职责的双份实现（如根目录与 tools 目录两套 check 脚本）都是隐患，必须收口、删除冗余。
- 基线/指纹/模板必须有且仅有一个版本，并随 `git` 一起提交（入库），杜绝"本机有、别人没有"。

```text
反例：check-interface.ps1（根目录） + check-interface.ps1（tools） → 口径不一致、结果矛盾
正解：仅 tools\check-interface.ps1 + 入库的 .interface-lock.json
```

## 原则二：规范必须可自证，而非靠自觉

- 检查工具必须能区分「合法变更 / 违规变更」，并给出明确处置指引（重建基线 or 还原文件）。
- 报错要带上可行动的信息：基线生成时间、对象最近提交时间、两种处置路径。
- 分不清的情况下，人就会绕开工具、不信任工具 → 规范名存实亡。

```text
正解（check-interface.ps1 逻辑）：
  结构一致         → [ OK ]
  结构变更 + 基线后未提交 → [WARN] 页面被误改 → git checkout 还原
  结构变更 + 基线后已提交 → [WARN] 需重建基线 → generate-interface-lock.ps1
```

## 原则三：阻塞分级，宁漏检不可误报

- 硬性阻断（中断构建/终止运行）只留给真正的红线，例如 APK 签名校验。
- 其余情况一律使用 Warn / 日志，避免工具误伤导致打包失败、用户闪退，否则工具会被弃用。
- 工具自身的解析失败必须降级处理（如基线时间解析失败→退回仅哈希比对），不得因工具问题误报。

```text
分级：
  红线（硬阻断）：APK 签名哈希校验
  关注（Warn） ：Root/调试器/Frida/Xposed、界面结构变更、基线过期
  记录（日志） ：DevTools 检测、反调试时间差
```

## 快捷自查清单

每个规范在落地时，对照三原则打勾：

- [ ] 权威源是否唯一、是否入库？
- [ ] 检查能否自证"合法 vs 违规"、报错是否有处置指引？
- [ ] 阻塞是否分级？是否遵循"宁漏检不可误报"？

## 落地映射（已自动化）

### 1. 8 处版本一致性 → `tools/verify-version-display.ps1`（合规 4b/9）

把原手工"检查 8 处版本标识"固化为自动门禁：
- 唯一权威源：全局版本展示值仅允许一种（当前 V1.0.0），任何独立硬编码背离即判矛盾。
- 可自证：逐一列出每个界面副本抽取到的版本 token，缺失/不一致都有可行动修复指引。
- 分级：出现 ≥2 种 token（确定矛盾）→ FATAL 阻止；无 token（模板不显示版本）→ WARN 不阻断。
- 用法：`powershell -File tools\verify-version-display.ps1`（已并入 `compliance-check.ps1`）。

### 2. 桌面 build.files 同步 → `tools/pre-build-check.js`（合规 6/9）

build.files 既是该桌面工程打包内容的唯一权威源，也必须自证：
- 唯一权威源：各桌面工程 `package.json` 的 `build.files` 各自唯一决定其 asar 内容。
- 可自证：新增强校验——每条 `build.files` 条目在磁盘上能否解析到文件（防拼写错、漏加脚本却只被 main.js 注入），与原有"index.html 引用 JS 必须被覆盖"形成双向校验。
- 分级：条目解析不到 → WARN 不阻断（可能为构建时生成的 node_modules 等）；JS 引用漏覆盖 → FATAL 阻止打包。已自动覆盖 cloud_desktop / db-offline/desktop 两端。
