### BUG-DB-04：SQLite 插件未同步导致离线处方"丢失"（★ 高频复发）

| 项目 | 内容 |
|------|------|
| **首次出现** | 2026-06-26 用户报告 |
| **修复 commit** | 参见 [debug-offline-prescription-lost.md](file:///c:/Users/61767/Documents/trae_projects/kyt-zy/docs/debug-offline-prescription-lost.md) |
| **症状** | 离线模式保存的处方，开通云端权限后历史处方列表为空 |
| **根因** | APK 构建时未执行 `npx cap sync android`，导致 `window.Capacitor.Plugins.CapacitorSQLite` 为 undefined，`LocalDB.available()` 永远返回 false，所有离线保存/读取逻辑被跳过 |
| **修复方式** | 执行 `npx cap sync android` 同步插件，重新构建签名 APK |
| **复发情况** | 用户第二次报告同样问题（首次修复未根治） |
| **复发原因** | 首次仅重新打包 APK，未在打包流程中固化 `cap sync` 步骤 |
| **永久根治方案** | 在 `build.bat` 打包脚本中增加 `call npx cap sync android` 前置步骤，确保每次构建都同步插件 |

### BUG-DB-05：SQLite 插件方法名错误

| 项目 | 内容 |
|------|------|
| **修复 commit** | `f59462f`（子模块） |
| **症状** | `sqlite.setSecret is not a function` |
| **根因** | `LocalDB.ready()` 调用 `sqlite.setSecret()`，但 vanilla JS 插件对象的正确方法是 `sqlite.setEncryptionSecret({passphrase:...})`。`setSecret` 是 `SQLiteConnection` wrapper 类的方法名 |
| **修复方式** | `setSecret` → `setEncryptionSecret`，参数 `secret` → `passphrase`，先 `isSecretStored()` 检查避免重复设置 |
| **复发情况** | 未复发 |
| **教训** | 混用 wrapper 类 API 和 vanilla 插件 API 是常见陷阱，需查阅插件源码确认方法签名 |

## 二、多端同步模块

### BUG-SYNC-01：allowedMode 默认值不一致导致状态显示矛盾（★ 高频复发）

| 项目 | 内容 |
|------|------|
| **首次出现** | commit `3004b4e` — 全项目统一重构 |
| **修复 commit** | `6d2fd30`、`e612668`、`5c49a06` |
| **症状** | 平台管理员/普通用户显示"离线"状态，但实际可以访问云端；或用户显示"仅离线"但实际有云端权限 |
| **根因** | `getUsers()` 中 `allowedMode` 默认值判断在不同位置使用了不同默认值（`local`、`both`、`platform_admin`），导致同一用户在不同界面显示不同状态 |
| **修复方式** | 统一 `allowedMode` 默认值为 `both`；`getUsers()` 中增加 `platform_admin` 角色判断 |
| **复发次数** | 3 次（三个不同 commit 修复同一类问题） |
| **复发原因** | 权限判断逻辑分散在多个函数中，每次只修一个位置，其他位置的默认值仍不一致 |
| **永久根治方案** | 提取统一的 `resolveAllowedMode(user)` 函数，所有调用点统一引用，禁止分散判断 |

## 五、权限模块

### BUG-AUTH-01：密码加密 btoa() 编码问题（★ 高频复发）

| 项目 | 内容 |
|------|------|
| **首次出现** | 用户反馈个人版 APP 修改密码提示"数据处理异常，请重试" |
| **修复 commit** | `bcaf29a`、`12740b7`、`e3faf21` |
| **症状** | 修改密码失败；密码包含中文等 Unicode 字符时加密/解密异常 |
| **根因** | `simpleEncrypt` 使用 `btoa()` 处理 XOR 后的字符串，`btoa()` 只能处理 ASCII/Latin1 字符，遇到 Unicode 字符抛出异常 |
| **修复方式** | 在 `btoa()` 前使用 `unescape(encodeURIComponent(result))` 预处理，在 `atob()` 后使用 `decodeURIComponent(escape(text))` 还原 |
| **复发情况** | 关联复发： |
| 1. 离线版 simpleEncrypt | `bcaf29a` — btoa() Unicode 问题 |
| 2. 云端网页版修改密码 | `12740b7` — 前端直接比较 password 字段（undefined）导致验证永远失败 |
| 3. 全版本 try-catch | `e3faf21` — 所有版本 handleChangePassword 添加异常捕获 |
| **复发次数** | 3 次 |
| **复发原因** | 1) 前端修改密码逻辑与后端不同步；2) 前端直接比较 `users[userIndex].password`（后端返回的用户对象不含密码字段，为 undefined）；3) 异步函数缺少 try-catch |
| **永久根治方案** | 1) 修改密码统一调用后端 `/users?action=change-password` 端点；2) 前端不存储/比较密码明文；3) 所有异步函数添加 try-catch；4) `btoa()`/`atob()` 统一使用 Unicode 安全包装 |

## 附录：关键教训总结

1. **多端代码必须同步**：同一功能在 7+ 个文件中实现，修改时必须全部同步，否则会出现"修了 A 端忘 B 端"的复发
2. **权限判断集中管理**：分散的权限判断是最高频 bug 来源，必须提取统一函数
3. **缓存策略需双维度**：兼顾"启动速度"和"更新及时性"，使用版本号机制
4. **编码函数注意字符集**：`btoa()`/`atob()` 不支持 Unicode，必须使用 `encodeURIComponent`/`escape` 包装
5. **移动端 API 降级**：`crypto.subtle` 等 Web API 在 WebView 中可能不可用，需准备降级方案
6. **打包流程固化**：`npx cap sync android` 必须固化在打包脚本中，不能依赖手动执行
7. **异步函数必须 try-catch**：所有 async 函数应添加错误捕获，避免未处理异常导致界面卡死
8. **简单功能不过度设计**：多用户名记住功能从后端 API 简化为 localStorage 是正确方向
9. **媒体处理需系统设计**：编解码、传输、渲染三个层面统一设计，不能逐个 patch
10. **数据完整性前置**：密码等必填字段应在数据创建时保证完整性，而非在运行时补丁
