## 一、结论（TL;DR）

**登录慢的主因只有一个，而且已修复上线**：

`functions/api/users.js:2358`（机构版 desktop/APP 登录的设备额度预检）调用了
`listLicenses(kv)` —— 1 次索引 get + **逐条 get 全部 license（实测 166 条）**，只为
`find(l => l.clinicName === clinicName)` 找一条记录。

| 指标 | 修复前 | P0 后 | P1 后（当前） | 累计 |
|---|---|---|---|---|
| **暖态登录** | 2,948 / 2,887 ms | 1,784 / 1,839 ms | **1,720 / 1,734 ms** | **−41%** |
| 认证后附加工作（对照实验差值） | ≈2,116 ms | ≈1,373 ms | **≈944 ms** | **−55%** |
| 冷启动首次登录 | 25,664 ms | 25,790 ms（**含一次性索引回填**） | 同（索引已就位） | 见下方说明 |
| 该分支 KV 读取次数 | **166 次串行 get** | **1–2 次 get** | 1–2 次 | **≈100×** |

> 注：以上为分钟级抖动下的多点取值（同批测量中偶见 2.2s/5.0s 的单次尖峰，属 CF/KV 冷热抖动）。

> **冷启动数字的说明**：修复后第一次登录的 25.8s 不是"没修好"，而是**索引当时还不存在**，
> 走了"全扫 + 懒回填"（一次性把 166 条读一遍建索引）。回填完成后索引已就位
> （生产实测：`license_clinic_index` 已登记 **18 个诊所 / 19 条授权码**，含
> `中医诊所·2222 → [BNZC-VSDU-…]`），此后登录稳定在 1.8s。
> 冷态残余耗时现在只与**操作次数**相关（约 15 次 KV/D1 往返），预期 ~2–3s。

**第二梯队收益点**（未做，见第五章 P1）：把 ≤2000 条处方全表塞进登录响应（响应体可达
1–5MB）；客户端对同一份处方做**四次全量 IO + 两次大 JSON 同步序列化**。

## 三、根因分析（分层）

### 3.1 服务端：单点 N+1 全表读 + 串行往返

- **主因**：`users.js:2358` 的 `listLicenses`（仅 `cloud_clinic` 机构版 + desktop/app 触发）。
- **服务端稳态开销**（机构版已索引化后）：KV 读 ≈15 / 写 ≈3 / 删 ≈2，D1 语句 4，crypto 3
  （PBKDF2 **100,000 迭代** + HMAC + SHA-256）→ 约 **8–10 个串行 RTT + 1 次 100k PBKDF2**。
- **串行结构**：`system:clinics`（`findUserForLogin` 内）→ `clinic:{id}:users` →
  `system:platform_admins` → `system:service_accounts` 为**诊所账号 100% miss 的 3 连读**，
  彼此无依赖却串行。

### 3.2 客户端：可见 ≠ 可用

- 「主界面可见」= 1 次登录 HTTP + 本地表哈希 + 约 13–20 次**同步**本地写（0.5–2s，网络主导）。
  **首屏处方不在这段路径上**（预取机制实现正确，`index.html:10829-10832` 确认被消费）。
- 但 `index.html:3181 await loadData()` 让"处方/序号/统计可用"多等一长串：其中
  `:10857` 全表读 IDB → `:10881` 清空 IDB → `:10882` **大 JSON 同步写 localStorage** →
  `:10883` 全量 put IDB = **同一份处方四次全量 IO**；n=2000 时 `JSON.stringify`
  5–20MB、同步阻塞主线程 100–600ms。这正是代码注释自承的"慢机/大处方库十余秒"。

## 六、度量与回归建议（让优化可量化、不反弹）

1. **服务端分段计时**：登录响应内输出 `Server-Timing` 或在日志打
   `[LoginTiming] t_ip=.. t_user=.. t_pwd=.. t_lic=.. t_bind=.. t_total=..`，
   否则下次"变慢"又要靠猜。
2. **客户端里程碑**：`performance.now()` 打点（请求发出 / 响应到达 / 主界面可见 /
   首屏数据可用），随现有遥测上报。
3. **登录基准纳入回归**：把 `e2e/.tmp/login-speed-measure.cjs` 固化为门禁项，
   门槛建议：**暖登 ≤1,200ms、冷登 ≤3,000ms**（当前 1,784ms / 待复测）。
4. **索引就绪性巡检**：部署后自动检查 `license_clinic_index`、`mid_owners`、
   `prescriptions_index`、`user_session_index` 是否已回填（避免"首次登录付回填代价"）。
5. **KV 配额**：读 10 万/天、写+删+**list 共 1000/天**；`list` 是历史降级根因，
   新增读路径一律禁止 `list`，优先"投影索引 + 懒回填"（本仓已有 4 个先例可照抄）。

### P1-④ 实施方案（**入口已穷尽**，可直接照做）

原先的判断是"需穷尽所有处方创建入口，风险高"。本轮把入口查清了 —— **不必 gate 7 个入口，
处方号生成只有一个收口点**：

| 项 | 位置 | 说明 |
|---|---|---|
| `generatePrescriptionNo()` 调用点 | `L4103`（首屏序号刷新，登录后即跑）、`L6447`（保存路径）、`L8205`、`L8400`、`L8477`、`L8845` | 共 7 处，涵盖打印/图片/复制/新处方等 |
| **唯一收口** `getGlobalMaxSerial()` | 定义 `L6263`；**仅 2 个调用点**：`L6422`、`L6429` | 读 `all_prescription_list`（localStorage）算最大序号 |
| 处方保存入口 | `savePrescription()` `L8681`、`savePrescriptionToDB()` `L2360`、`savePrescriptionAsImage()` `L8931` | 保存时也会取号 |

**做法（最小且可验证）**：

1. `loadData` 在 `prescriptionHistory = result` 赋值处（约 `L5679`）**成功与失败两条路径都**置
   `window.__prescriptionsReady = true` 并 resolve `window.__prescriptionsReadyPromise`
   （失败路径也必须置位，否则标志永久 false ⇒ 卡死开方 ✗）。
2. `getGlobalMaxSerial()` 开头 `await` 该 Promise（**带超时，建议 10s**）：
   - 就绪 → 照常算最大序号 ✓
   - 超时/未就绪 → **fail-closed**：不取号、给明确中文提示（"处方数据仍在加载，请稍候再开方"）
     —— 医疗场景下"拒绝一次开方"远优于"生成重复处方号" ✗
3. 主界面仍可提前显示（fire-and-forget `loadData()`），但依赖处方数据的动作被上面这一处 gate 拦住 ⇒
   **感知延迟从"等十余秒"变成"界面立刻出现、数据随后到"**，而序号完整性由收口点保证 ✓
4. 断言（与已入库的门禁同风格，按函数本体抽取）：`getGlobalMaxSerial` 在未就绪时不返回值、
   在就绪后返回 == 既有最大序号 + 1 的值；且未就绪时的调用**不会写入任何存储**（不得留下半成品序号）

> 收口点只有一处，是本轮最重要的发现 —— 它把 P1-④ 从"高风险"降为"小改动 + 一条断言"。仍须遵守
> 本仓铁律：**先立断言再改代码**，且 `getGlobalMaxSerial` 在离线桌面权威源同体 ⇒ 改动须同步离线端并过跨版本门禁。
